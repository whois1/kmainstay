# K-Mainstay MVP Chat Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Deliver one working VPS-hostable web application where Michael logs in, creates a bot user, copies its API key, and exchanges persistent Markdown messages with that bot in an organisation-wide `general` conversation.

**Architecture:** One Go modular monolith exposes the HTTP API, WebSocket endpoint, and embedded Vue application. SQLite in WAL mode stores all state. Caddy terminates TLS on the VPS and proxies to one systemd-managed Go process. Humans and bots share the same `users`, organisation membership, conversation, and message model; only authentication differs.

**Tech Stack:** Go standard `net/http`, `database/sql`, `modernc.org/sqlite`, embedded SQL migrations, Argon2id, Vue 3, TypeScript, Vite, Vue Router, safe Markdown rendering, WebSocket, SQLite, systemd, Caddy. No ORM initially; the database package is an explicit boundary where one can be introduced later if handwritten SQL becomes a demonstrated maintenance cost.

---

## Confirmed MVP scope

### Included

- One manually bootstrapped Michael account with email/password login.
- Data model supports multiple organisations, but the first UI uses one organisation.
- Users have `human` or `bot` type and otherwise share the same chat model.
- Organisation-wide named conversations.
- Private conversations with selected users represented in the schema/API, but the first vertical UI path may remain `general` only until the core path works.
- Plain chronological messages rendered as safe Markdown with code blocks.
- Bot creation with one copy-once API key.
- Bot HTTP API and WebSocket feed.
- Complete bot messages only; no response streaming.
- Bot marker/icon beside the name; otherwise bots look like humans.
- One Go process on one VPS with one SQLite file.

### Excluded

- Docker, PostgreSQL, Redis, queues, microservices, GraphQL, and Kubernetes.
- Public registration, human invitations, password reset, and email delivery.
- Threads/replies, files, reactions, message editing/deletion, search, and notifications.
- Streaming responses, typing/reasoning/activity events, or agent orchestration.
- Fine-grained roles, permissions, API-key scopes, and enterprise controls.
- Native desktop and mobile applications.

## Acceptance path

1. Start the application against a new SQLite file.
2. Bootstrap Michael and the default organisation from a one-time CLI command.
3. Log in through the Vue web app.
4. Open `general` and post a Markdown message.
5. Create bot user `Hector` and copy its API key from the one-time display.
6. Connect a small reference bot client using that key.
7. Post another message from Michael.
8. Observe the event in the bot client.
9. Have the bot post one complete reply.
10. Observe the reply in the browser without refreshing.
11. Restart the Go process and confirm users, conversation, and messages persist.
12. Confirm an invalid/revoked bot key cannot read or send messages.

**Objective:** Deliver persisted messages over WebSocket to authenticated users without response streaming.

**Endpoint:**
- `GET /api/events` upgraded to WebSocket, authenticated by human session cookie or bot bearer key.

**Minimal event envelope:**

```json
{
  "version": 1,
  "id": "evt_...",
  "type": "message.created",
  "occurred_at": "...",
  "organisation_id": "org_...",
  "conversation_id": "conv_...",
  "data": {"message": {}}
}
```

**Reliability rules:**
- Persist message and corresponding event in the same transaction.
- Client supplies its last acknowledged event ID on reconnect.
- Replay accessible missed events, then switch to live delivery.
- A slow/disconnected client must not block message persistence or other clients.
- Every organisation message reaches every organisation member, including bots.
- Private conversation events reach only participants.
- Agent-authored events reach other bots too; bot behaviour determines whether to respond.
- Add a conservative per-key request/message rate limit and duplicate client-message ID handling to mitigate accidental loops.

## Principal risks and controls

### API key copied into an agent conversation

The key is a credential and may enter local session history. The UI must say so plainly. Scope is limited to one bot identity, keys are revocable, and rotation is easy. Fine-grained scopes remain deferred.

### Bot loops

Delivering bot-authored messages to bots is intentional. Prevent infrastructure damage with rate limits, client-generated idempotency keys, maximum message size, and an emergency key revocation path. Do not make the server decide whether an agent should respond.

### SQLite contention and durability

One process, WAL mode, short transactions, bounded busy timeout, and tested backups. Do not add horizontal instances while using SQLite.

### WebSocket delivery gaps

Persist before fan-out; replay by durable event ID. Do not claim exactly-once delivery. Client deduplication is required.

### Markdown XSS

Store source text, render with raw HTML disabled, restrict URL schemes, and test malicious payloads. Do not trust bot-authored content.

### Premature abstraction

Do not implement future runtimes, projects, instructions, skills, memory, activity, or permissions. Preserve only low-cost schema boundaries that the current model directly requires.

## Backend TDD evidence — 2026-08-14

The starting compile RED was the previously verified `go test ./...` failure in
`internal/httpapi/router.go`: `botID` was assigned without being declared. The
minimal fix was a local declaration (`botID := database.NewID("usr")`).

Subsequent RED/GREEN cycles run in this continuation:

1. **Realtime restart replay**
   - RED: `go test ./internal/httpapi -run TestBDD_MichaelAndHectorExchangePersistentRealtimeMessagesAndRevocationSurvivesRestart -v` compiled, then failed at `integration_test.go:125` with `context deadline exceeded` while reading the replayed event.
   - Cause: with SQLite restricted to one connection, the replay handler held query rows open while performing a nested event query.
   - GREEN: after collecting event sequences and closing the rows first, the same BDD test passed five consecutive runs with `-count=5` (`ok kmainstay/internal/httpapi 3.751s`).

2. **Generated bearer-key parsing**
   - RED: repeated BDD runs intermittently returned `401 authentication required` for a newly generated valid key.
   - Cause: URL-safe key secrets can contain `_`, but authentication used an unbounded `strings.Split`.
   - GREEN: parsing with `strings.SplitN(..., 4)` made the valid key stable; the five-run BDD command above passed.

3. **Bounded chronological pagination**
   - RED: after adding assertions for `?limit=1`, the BDD test received both messages instead of only the newest page.

   - GREEN: validating that the cursor belongs to the requested conversation changed this to the required `400`, and the BDD test passed.
